Create the identity schema later M2 tasks build on. This task adds only
the 0002 migration with organizations, users, and memberships, plus

any business logic beyond the schema constraints.

Required behavior:
1. Add opsledger/migrations/0002_identity.sql creating three tables:
   a. organizations (id TEXT PRIMARY KEY, slug TEXT NOT NULL UNIQUE,
      name TEXT NOT NULL, created_at TEXT NOT NULL).
   b. users (id TEXT PRIMARY KEY, email TEXT NOT NULL UNIQUE,
      display_name TEXT NOT NULL, created_at TEXT NOT NULL).
   c. memberships (organization_id TEXT NOT NULL REFERENCES
      organizations(id), user_id TEXT NOT NULL REFERENCES users(id),
      role TEXT NOT NULL CHECK (role IN ('developer','lead','auditor',
      'approver','purchasing')), created_at TEXT NOT NULL,
      PRIMARY KEY (organization_id, user_id)).
2. Normalized identity, enforced by the schema:
   - organization slugs are stored lowercase-trimmed and unique;
     duplicate or different-case slugs are rejected (UNIQUE on the
     stored normalized value).
   - user emails are stored lowercase-trimmed and unique; duplicate or
     different-case emails are rejected.
3. One organization may not contain the same user twice: the
   (organization_id, user_id) primary key rejects a second membership;
   a plain INSERT of a duplicate must fail with sqlite3.IntegrityError.
4. Parameterized SQL everywhere; created_at values are RFC3339 UTC
   ending in Z with second precision.
5. Add tests under tests/unit/test_identity_schema.py covering:
   - a fresh database migrates 0001 then 0002; running migrate again
     is a no-op.
   - a unique slug inserts; the same slug again raises IntegrityError;
     a different-case slug (normalized the same) is rejected because
     the stored value collides.
   - a unique email inserts; the same email again raises
     IntegrityError; a different-case email is rejected the same way.
   - a membership inserts; a duplicate (organization_id, user_id)
     raises IntegrityError (the cross-organization relationship is
     rejected: the same user in a different organization is fine, the
     same user twice in one organization is not).
   - an unknown role value is rejected by the CHECK constraint.
   - a membership referencing a missing organization or user fails the
     foreign key.
6. Update docs/architecture.md with the 0002 tables, their columns,
   the normalization rule (slug and email stored lowercase-trimmed),
   and the membership key (one row per organization+user).
